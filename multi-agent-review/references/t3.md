# T3 V2 execution

## Discovery and exact targets

Call `orchestrator_capabilities({})` at the start of the review. Use current `providers[]`, `canRunChildTask`, `canRunCrossProviderChildTask`, `constraints`, and each model's `options`. Provider IDs and enabled/authenticated state can change. A model in the catalog does not imply the provider can currently run it.

  {"providerInstanceId":"claudeAgent","model":"claude-opus-5-5","options":{"effort":"xhigh"}},

Refresh option IDs as well as availability: the Cursor Grok 4.7 effort option has appeared as both `reasoning` and `reasoning_effort` in live catalogs. Set `fastMode: false` explicitly when supported to preserve the standard-tier preset. A successful launch does not prove completed inference; terminal metadata may confirm the model without attesting effective effort. The CLI separately uses the listed `grok-4.7-xhigh` alias. Test each transport independently and do not copy authentication secrets between them.

## Launch, retain, and collect

The skill explicitly requests T3-owned children for both same-provider and cross-provider reviewers. Native same-harness subagents are not the T3 path for this skill: even a Claude coordinator's Claude reviewer is a new `delegate_task`, with a distinct task ID and no inherited conversation history.

For each reviewer, call the actual exposed tool, for example:

```json
{
  "task":"Complete self-contained review brief, exact inputs, scope, read-only constraints, and required findings format",
  "title":"Review: Claude / round 1",
  "role":"review",
  "mode":"async",
  "interactionMode":"plan",
  "target":{"providerInstanceId":"claudeAgent","model":"claude-opus-5-5","options":{"effort":"xhigh"}},
  "clientRequestId":"REVIEW_RUN_ID-claude-r1"
}
```

`plan` requests a non-editing interaction mode; verify provider support. It does not mean an OS-enforced read-only filesystem. Keep explicit review-only constraints in the task. Do not escalate inherited runtime permissions for a review.

T3 child prompts do **not** copy parent conversation history. Include all needed user requirements, paths and source pointers. Delegation inherits the caller's project/branch/worktree and has no workspace override. Giving a child a different `cd` command does not change its T3 binding; if files are elsewhere, state that explicitly and use verified read access or a CLI with an explicit working directory.

For a preserved source snapshot, name its absolute path and manifest hash in the brief. Require the child to inspect that copy and report its start/end verification, even though its T3 binding remains the original worktree. If that path cannot be read, the review is blocked; do not let the child silently review newer live files instead.

Persist the returned `taskId`, `childThreadId`, selected model/provider, request ID, and status in the run manifest. Use `taskId` for `task_status` and `task_cancel`. `childThreadId` is backing storage, not a new-round API.

Async completion wakes the parent. Continue independent synthesis/preparation; if only child work remains, yield and let the notification resume the task. Do not create a polling watcher. Use `task_status` when a result is needed during an active turn. A `mode: wait` timeout only ends the parent's wait; it does not cancel the child, so do not duplicate the launch.

Record the launch time and the shared reviewer budget (default 15 minutes), and include it in the child's brief. The observed T3 API has no hard execution-deadline parameter: `timeoutMs` only bounds a waiting tool call. At the next active opportunity after the deadline, inspect `task_status`; if still active, call `task_cancel`, then confirm the terminal outcome before recording `timed_out`. A `cancel_requested` response is not terminal confirmation. If a result arrived before cancellation, retain it and record its actual timing rather than relabeling it cancelled.

Do not promise an automatic cutoff while the parent is yielded. If the user requires a hard deadline, select a verified host cancellation facility or a supervised CLI process before launch. Do not invent a task TTL or create a persistent scheduler/polling watcher to compensate. If cancellation cannot be confirmed, show an interim report with the active-task limitation and retain ownership of its handle; do not call the workflow finished.

Inspect `status`, `workState`, and the published `summary`. A completed turn with `workState: waiting_for_children` is not a finished review. Track explicit failures/cancellation separately. `latestTerminal*` and later pending child-thread runs do not change the original published task result.

If a launch reply is lost, retry only with the same `clientRequestId` for that exact run. A new reviewer/round gets a new key. Keep a bounded launch-recovery attempt; do not switch transports until the original launch is known not to be active. On cancellation, use `task_cancel({taskId, reason})` and verify its outcome.

For a challenge round, call `delegate_task` again with the original brief, prior findings, responses, and unresolved objections. Do not use `t3_thread_send` to continue the backing thread. Do not use `t3_thread_launch` or `create_threads`; those create ordinary top-level conversations.

## Lazy tools and ACP fallback

Search the active tool catalog for normalized names such as `mcp__t3_code__orchestrator_capabilities`. If T3 is expected but absent, make one bounded direct call using the known name before declaring it unavailable.

Some ACP harnesses receive the T3 server without exposing its tools. If `T3_ACP_MCP_NODE` exists, this is the supported transport fallback:

```sh
ELECTRON_RUN_AS_NODE=1 "$T3_ACP_MCP_NODE" ${T3_ACP_MCP_ENTRYPOINT:+"$T3_ACP_MCP_ENTRYPOINT"} acp-mcp-call orchestrator_capabilities '{}'
```

Call `delegate_task`, `task_status`, and `task_cancel` through the same transport with JSON arguments. For substantial prompts, construct the argument via a JSON serializer and invoke the process with an argument array (e.g. Python `subprocess.run`), not interpolated shell text. Preserve the same IDs and lifecycle as MCP. An unavailable ACP transport leads to the CLI fallback, not top-level T3 threads.
